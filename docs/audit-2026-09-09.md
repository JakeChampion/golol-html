# Multi-lens review and audit — 2026-09-09

**Scope:** the full repository at commit `fc6ce92` (v0.2.1) — the Go API (`lolhtml.go`, `rewriter.go`, `element.go`, `endtag.go`, `streaming.go`, `rawtext.go`, `options.go`, `errors.go`, …), the cgo boundary (`shim.c`, `shim.h`, `cfuncs.go`, `callbacks.go`, `strings.go`, `handles.go`), the documentation (`README.md`, `SPEC.md`, `CHANGELOG.md`, `docs/`, every doc comment), build/CI/release/supply chain (`Makefile`, all five workflows — `release.yml` and `verify-native.yml` for the first time — `scripts/`, the vendored archives and header), the three test suites and both fuzz targets, the 171 example applications, and the fixes made for the previous audit.

**Method:** ten independent review lenses ran in parallel — cgo/memory safety, API semantics, lifecycle/concurrency/panic containment, security of untrusted input, docs parity, build/CI/supply chain, test quality (by mutation: 23 deliberate corruptions, 8 survived), performance/allocation, the example applications, and a regression check of every fix from the 2026-08-28 audit. Their 84 raw findings deduplicated to 66. Every high and medium finding was then handed to a separate verifier instructed to refute it against a pristine clone with its own probes; the two high findings had two independent verifiers each. Sixteen findings went through that round: 15 confirmed as stated, 1 confirmed but downgraded (F-05), 0 refuted. Low and informational findings carry the lens's own probe evidence. A completeness pass records what no lens covered.

**Headline result:** the boundary work of the previous audit held — no memory-unsafety reachable from untrusted HTML was found, the reentrancy and panic containment of #334 survived adversarial re-probing, and every archive, header, pin and action SHA checked out. The defects this time are one layer up. The raw-text breakout guard, the documented safe path for inserting untrusted content into a script or style, lowercased with a Unicode fold and sliced the caller's string with an offset into the lowered copy: a panic on content containing U+023A, and a false refusal on U+0130. The `csrf` example, teaching code with a security purpose, inserted the token into a form whose entity-encoded `action` posts to another origin. Panic containment had a third way out it did not know about, `runtime.Goexit`, which is what `t.Fatal` inside a handler does. `EndTag.SetName` accepted names `SetTagName` refuses, including `>`. And the release workflow added since the last audit has two state-machine holes and a gate that has never gated a release. Behind those: two allocation-class costs on the streaming and mutation paths, a leak-backstop test that could not fail, and a tail of documentation that drifted again in the release that fixed the last drift.

## Findings

### High

#### F-01 — The raw-text breakout guard lowercases inserted content with a Unicode fold and slices the caller's string with an offset from the lowered copy

*`rawtext.go:284`, `rawtext.go:234` — defect — high — verified by three lenses and two independent verifiers*

`findClosingTag` did `lower := strings.ToLower(content)` and searched `lower` for `"</"+tag`; `checkRawText` then quoted `content[i:…]` with the `i` found in `lower`. `strings.ToLower` is full-Unicode and not length-preserving: U+023A (Ⱥ) and U+023E (Ⱦ) grow from two bytes to three, and 23 other runes shrink. So `lolhtml.CheckRawText("script", strings.Repeat("Ⱥ", 10)+"</script>")` panicked with `slice bounds out of range [30:29]`, and the same panic came out of `Element.Append`, `Prepend`, `SetInnerContent` and `EndTag.Before` with `HTML` content — re-raised on the goroutine that called `Write`, poisoning the Writer. Those are exactly the paths the documentation names as the safe way to insert untrusted text into a script or style. Two more consequences of the same fold: U+0130 (İ) lowercases to ASCII `i`, so `</scrİpt>` was refused although lol-html's ASCII-only tokenizer does not end the script there (verified: `<script>a</scrİpt><img src=x></script>` reports only `script`), and `IsRawText("scrİpt")` answered true for an element that holds markup; and for any of the shrinking runes the offset and quoted bytes in the error were wrong, sometimes splitting a rune. Pinned behaviour B129 says case folding is ASCII everywhere it happens; this was the one place it was not.

Fixed here: the guard, `IsRawText`, `DecodesCharacterReferences` and `checkRawText` fold ASCII only, and the search is a byte loop over the caller's string, so no offset is ever derived from a copy. `Element.content` borrows the tag name from lol-html for the check instead of copying it (see F-37).

<details><summary>Evidence</summary>

Verifier 1: `PANIC CheckRawText("ȺȺȺȺȺȺȺȺȺȺ</script>"): runtime error: slice bounds out of range [30:29]`; the threshold is exactly ten Ⱥ; with fewer the offset is wrong instead. `Append` of the same content inside `OnElement("script")` panics out of `RewriteString`. `CheckRawText("script", "</scrİpt>")` refused; rewrite of `<script>a</scrİpt><img src=x></script>` under `OnElement("*")` yields `[script]` only. Verifier 2 reproduced all three independently and traced the whole-Unicode census: two growers, 23 shrinkers.

</details>

#### F-02 — The `csrf` example inserts the token into a form whose entity-encoded or backslash `action` posts to another origin

*`examples/gip/csrf/main.go:293` — defect (teaching code) — high — verified by the examples lens and two independent verifiers*

`ours()` ran `url.Parse` on the raw attribute source and treated anything with no scheme and no host as a same-origin relative URL. `Element.Attribute` returns source text with character references intact (documented, B-rows on attribute values), a browser decodes them at tokenisation before resolving the URL, and the WHATWG URL parser turns `\` into `/` for special schemes. So `action="&#104;ttps://evil.example/steal"`, `action="https&#58;//…"`, `action="\\evil.example/x"`, `action="/\evil.example/x"` and an encoded `formaction` on a submit button were all judged same-origin, the token was inserted, and the program exited 0 reporting "1 tokens inserted" — while the plain `https://evil.example/steal` was refused correctly. That is the same raw-versus-decoded class PR #335 fixed in `email`, `mixed`, `cspnonce` and `redact`; `csrf` was the member of the class the examples audit did not list, and its test suite contains no character reference at all.

Fixed here: `csrf` decodes, strips leading control characters and whitespace, normalises backslashes and fails closed; each bypass is a test row.

<details><summary>Evidence</summary>

Verifier 3: `printf '<form method=post action="&#104;ttps://evil.example/steal">…' | csrf -token=SECRET -origin=https://me.example` → token inserted, exit 0; same for `\\evil.example/x`, `/\evil.example/x`, `&#47;&#47;evil.example/x`, and an encoded `formaction`; plain `https://evil.example/…` → "1 cross-origin", exit 1. x/net/html tokenizer oracle decodes each to a cross-origin URL. Verifier 4 reproduced with `&#x68;` and `https&#58;//` variants and confirmed `grep '&#' examples/gip/csrf/` is empty.

</details>

### Medium

#### F-03 — `runtime.Goexit` from user code is not a panic, so the containment of #334 parks nothing, lol-html's frames are skipped, and the deferred Close finishes an abandoned rewriter with nil

*`callbacks.go:96`, `rewriter.go:412` — defect (incomplete fix of last audit's F-01/F-02) — medium — verified by two lenses and one verifier*

`t.Fatal`, `t.FailNow` and `t.Skip` inside a handler closure — the way assertions are written inside handlers, and this repository does it in four places — call `runtime.Goexit`. `recover()` returns nil during a Goexit, so `runHandler` and `writeSink` parked nothing and returned no STOP; Go's `cgocallbackg1` then unwound the C and Rust frames exactly as on a panic (confirmed from the Go 1.24.7 source: `_panic{goexit:true}`, `gorecover` nil, deferred `unwindm`). With `panic = "abort"` those frames have no landing pads, so the `Element` and mutation list they owned were never dropped. Back in Go, `Write`'s deferred `endCall` saw no panic and left the Writer neither poisoned nor closed; the caller's deferred `Close` (including `Rewrite`'s own) then ran `lol_html_rewriter_end` on a rewriter abandoned in the middle of `parser.parse` — the second `&mut` alias `ErrReentrant` exists to prevent — and returned **nil** for a document truncated at `<html>`. A further `Write` on the abandoned Writer was accepted. One cgo handle leaked per streaming insertion pending in the abandoned frame (334 over 500 rounds, 2,000 over 3,000). No abort in 3,500 probe rounds, which is the same luck the last audit recorded for F-01.

Fixed here: `endCall` treats "`inCall` still set when the deferred call runs" as a call that never returned, whatever the way out, and poisons and releases the Writer; streaming handles are tracked on the Writer so `release` reclaims the ones whose drop was skipped; `Close` reports `ErrPoisoned`. The verifier confirmed `lol_html_rewriter_free` on the abandoned rewriter is a plain box drop with no callback into Go, the same Rust state the panic path already frees.

Handle leak +1 per pending streaming insertion. With the fix applied to a scratch copy: every site reports `ErrPoisoned` with a cause, full suite passes. The lifecycle lens's AST scan: `insertion_test.go:113`, `properties/sanitiser_test.go:259,264,273` use the shape.

#### F-04 — `EndTag.SetName` performs no validation, so a name from data silently produces a token that is not an end tag

*`endtag.go:51` — defect / contract drift — medium — verified by two lenses and one verifier*

lol-html validates a start tag's new name (empty, first character not an ASCII letter, and whitespace, `/`, `>` are refused with a message each) and does not validate an end tag's, requiring only UTF-8. The binding added nothing, so `SetName("a>b")` on `<div>x</div>` emitted `</a>b>` — re-parsed, an end tag named `a` followed by the text `b>`, and the div never closes; `SetName("")` emitted `</>`, which the tokenizer drops; `SetName("1a")` emitted a bogus comment; `SetName("script><img src=x onerror=alert(1)><x")` emitted a live `<img>`. No error in any row. The doc warned only that renaming one side "produces mismatched markup". The exposure is lower than F-01 because a name is usually program-chosen, but a rewrite that derives it from the document inherits an injection its sibling is protected against.

Fixed here: `SetName` refuses the same names `SetTagName` refuses, with lol-html's own messages, before the cgo call; invalid UTF-8 is still left to lol-html so it classifies as `ErrInvalidUTF8`.

#### F-05 — A selector nested a few thousand levels deep overflows the native stack and aborts the process

*`options.go:397` — defect (upstream, unguarded) — rated medium by the security lens, downgraded to low by its verifier — verified*

`:not(` × 3,114 (an 18.7 KB selector) SIGSEGVs inside `golol_selector_parse`; `div > ` × ~14,135 inside `golol_rewriter_build`; selector lists are fine to 131,072. It is a native stack overflow during a cgo call, so a goroutine, `debug.SetMaxStack` and `recover` change nothing and only `ulimit -s` moves the threshold. Downgraded because it is construction-time (untrusted HTML cannot reach it), upstream lol-html v3.0.1 behaviour, and needs an application that builds selectors from untrusted input — but it was ruled on nowhere, and the documented contract is that an unusable selector fails from `NewWriter` with a `SelectorError`.

Fixed here: `parseSelector` refuses more than 32 levels of parenthesis nesting or 128 combinators with a `SelectorError` naming the limit, counted outside brackets and quoted strings; both limits sit a hundredfold below the measured thresholds and far above any real selector. Pinned in `selector_test.go`.

#### F-06 — Two fragments with different bump levels open two release PRs; merging the older one leaves a version heading that is never tagged

*`.github/workflows/release.yml:91`, `scripts/changelog.sh:115` — defect — medium — verified by probe (scratch repo driving the real script) and one verifier*

The release branch carried the version in its name. A `patch` fragment opened `release/v0.2.2`; a `minor` fragment merged before that PR made the next run compute v0.3.0 and open a second PR, `release/v0.3.0`, leaving the stale one open and mergeable. Merging it put `## v0.2.2` on main with the minor fragment still pending; the plan step checked "fragments pending → propose" before "untagged heading → tag", so v0.2.2 was folded but never tagged, and after v0.3.0 merged the plan step's `grep -m1` tagged only v0.3.0.

Fixed here: one release branch regardless of version, `release/next`, refreshed on every push; and the plan step tags an untagged heading before proposing.

#### F-07 — A folded-but-untagged section plus any pending fragment fails every later release run; the concurrency group can drop the fold commit's run

*`.github/workflows/release.yml:27`, `scripts/changelog.sh:148` — defect — medium — verified by probe and one verifier*

`--next-version` derived from tags alone, so with `## v0.2.2` folded and untagged and a fragment pending, `--release` refused with `already has a '## v0.2.2' section` on the fold commit and every push after it, until someone hand-tagged. Reachable through a merge-order window of a minute or two, and through the workflow's concurrency group: GitHub's default `queue: single` cancels a *pending* run when a newer one queues, independent of `cancel-in-progress: false` (verified from docs.github.com), and the tag step tagged `HEAD`, so the surviving run could tag a later commit than the fold.

Fixed here: `--next-version` takes the max of the newest tag and the newest heading; the tag step tags the fold commit; the concurrency group no longer drops queued runs.

#### F-08 — The release gate has never gated a release: v0.2.1 was tagged with the default token and no workflow ran on the tag

*`.github/workflows/release.yml:125`, `.github/workflows/verify-native.yml:23` — hardening — medium — verified from the Actions history by the lens and a verifier*

The tag was pushed with `github.token` unless `RELEASE_PR_TOKEN` was configured, and it was not: the run for `fc6ce92` logged `HAS_TOKEN: false` and its own warning that ci and verify-native did not run on v0.2.1. ci.yml has zero runs on that tag (v0.2.0, pushed by a person, has one); verify-native has one pull_request and two scheduled runs and none on a tag. Even with the token, the gate was post-hoc — the tag exists and the proxy can serve it before the run is red — and the one PR whose merge becomes the tag touches only `CHANGELOG.md` and `changelog.d/`, which verify-native's `paths` filter never matches. Nothing bad shipped: ci ran on the same SHA as a main push and the weekly job reproduced linux/amd64 from it three days later.

Fixed here: `release.yml` reproduces the archive in-process before the tag step (a `reproduce` job the `tag` job needs, calling `verify-native.yml` as a reusable workflow at the fold commit), and `CHANGELOG.md` is in verify-native's `pull_request` paths filter so the release pull request gets the check before merge.

#### F-09 — `Sink.WriteChunk` copies every chunk into a Go string to inspect its last four bytes

*`streaming.go:208` — defect (allocation in the wrong class) — medium — verified by two lenses and one verifier*

`s.trackTail(string(b))`: the conversion does not escape, so the compiler uses a 32-byte stack buffer for small chunks and `mallocgc` above that. `io.Copy(s.AsWriter(HTML), r)` — the README's recommended shape for "content that is large or produced incrementally, so nothing has to be assembled in memory first" — allocated 12.6 MB/op for a 12.6 MB stream, the same bytes the buffering route it is documented as the escape from. Fixed here: `trackTail` is handed the last four bytes only; the same stream now allocates under 1 KB, and `alloc_test.go` gates it.

#### F-10 — The `cerr` out-parameter heap escape fixed for `Write` remained on every other hot C call

*`strings.go:101`, `strings.go:116`, `element.go` (four sites), `streaming.go` (three sites) — defect (incomplete fix) — medium — verified by the performance lens and one verifier*

CHANGELOG v0.2.0 describes the mechanism — the address of a local `C.lol_html_str_t` escapes, one 16-byte allocation per call — and fixed it for `Write` with `native.cerr`. The identical pattern remained in `withContent`, `withName`, `HasAttribute`, `SetAttribute`, `RemoveAttribute`, `OnEndTag`, `withStream` and both Sink writes: 13 distinct `moved to heap: cerr` sites, nine per-match. Every mutating call cost 2 allocations per match where the wrapper is 1. Sharing the Writer's slot is safe: the shim writes it only after the failing call returns, every reader takes the message out in the same instant, and a Writer is neither concurrent nor reentrant (verifier 4: 3,000-iteration double-failure hammer under `MALLOC_CHECK_=3`). Fixed here: every mutation is one allocation per match; the two gates that pinned "2" now pin "1" and "write ≤ read".

#### F-11 — `TestUnclosedWriterIsReclaimed` cannot fail

## What the audit did *not* cover

- **No AddressSanitizer or non-Linux execution.** Every lens ran on linux/amd64 with go1.24.7; the darwin, windows and musl rows are covered by reading the link files and by CI's history, not by running. The Goexit-then-Close shape (F-03) was probed 3,500 times without a detector; the claim of Rust-side undefined behaviour rests on the Go runtime source and the pinned c-api source, and the fix rests on a verifier's reading of `lol_html_rewriter_free`.
- **`native.yml` was reviewed by reading only.** It is `workflow_dispatch` and has no run in the history to read; the attestation step and the artifact hand-off between its jobs were not exercised. `make attest-verify` could not be run (no `gh` with attestation support here), so whether the archives currently carry attestations is unknown. Branch-protection and required-check configuration are not visible from the repository.
- **~149 example applications were grep-scanned, not read.** The 22 security-flavoured ones were read in full; the rest were scanned for ignored `Close`/`io.Copy` errors, retained units and per-chunk token patterns, and for `url.Parse` on an undecoded attribute (the F-02/F-13 class), and nothing beyond what the examples audit already fixed was found. A line-by-line read of each, as the 2026-08-28 examples audit did, was out of scope.
- **The escaping oracles' sensitivity was assessed by inspection, not by a mutation harness.** The properties and differential harnesses feed the guard and the escapers essentially ASCII payloads, which is why F-01 was reachable; a mutation study of which escaping regressions those oracles would miss was not done.
- **Engine-driven fuzzing was not run beyond 30–40 s per target.** The seed corpora were run; the new FuzzOperations oracle was checked against a short engine run only.
- **`CHANGELOG.md`'s v0.2.0 body** (some 4,800 lines) was read by targeted grep; the head, the reentrancy/selector/destination-panic entries, v0.1.x and "Behaviour worth knowing" were read in full.
- **Upstream lol-html's own panic surface** beyond the selector depth (F-05) was spot-checked with a twenty-document hostile set (megabytes of `<`, `<!--`, 100k-deep nesting, 100k attributes, 5 MB values, NUL-heavy, invalid-UTF-8-heavy, esi, plaintext, CDATA), all bounded and panic-free, not fuzzed.

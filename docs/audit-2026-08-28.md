# Multi-lens review and audit — 2026-08-28

**Scope:** the full repository at commit `d3f7c0c` — Go API (`lolhtml.go`, `rewriter.go`, `element.go`, `options.go`, `streaming.go`, …), the cgo boundary (`shim.c`, `shim.h`, `cfuncs.go`, `callbacks.go`), documentation (`README.md`, `SPEC.md`, `docs/gip/`), build/CI/supply chain (`Makefile`, `.github/workflows/`, `scripts/`, vendored archives), and the test/fuzz suites.

**Method:** eight independent review lenses ran in parallel (cgo/memory safety, API correctness, concurrency/reentrancy, security, error paths & resource lifecycle, docs parity, build/CI/supply chain, test quality). Their 36 raw findings were deduplicated to 30, and every surviving finding was then adversarially verified by separate agents instructed to refute it by re-reading the code (two independent verifiers for high-severity claims). 29 findings were confirmed, 1 was refuted and is recorded in the appendix. A final completeness pass identified residual areas the audit did not cover; those are listed honestly as gaps.

**Headline result:** the codebase is in very good shape — the audit found no exploitable memory-unsafety reachable from untrusted HTML input, and the invariants the code documents for itself are almost all enforced and tested. The confirmed defects cluster at the edges: two related gaps in the panic/reentrancy containment story at the cgo boundary (the only high-severity items), one lifetime-contract violation on `NewWriter` error paths that is currently benign, and a tail of documentation drift, CI/supply-chain hardening opportunities, and fuzz-coverage gaps.

#### F-01 — golol_sink_cb runs the user's destination io.Writer with no recover, so a panicking destination unwinds a Go panic across lol-html's Rust frames

*`callbacks.go:178` — cgo-callback-panic — verified: confirmed*

Every other //export'ed callback that runs user code goes through runHandler, which recovers panics and parks them so the Rust call returns normally (the file's stated invariant, callbacks.go:18-20: 'No Go error or panic may cross into Rust'). The output-sink callback is the exception: golol_sink_cb calls cb.c.st.dst.Write(b) — arbitrary user code — with no recover. A panic there propagates from the C->Go callback back to Writer.Write via Go's panic-through-C mechanism, abandoning the active lol_html_rewriter_write Rust frames without running their destructors. The vendored static libraries are built with panic="abort" (SPEC.md:37, :87), so those frames have no unwind cleanup and are skipped longjmp-style — Rust-side leaks and formally undefined behavior for foreign unwinding over Rust frames. releaseOnPanic (rewriter.go:202, 354-360) then calls lol_html_rewriter_free on a rewriter abandoned mid-write; streaming-handler drop callbacks owned by skipped frames never fire, leaking cgo.Handles (the exact hazard callbacks.go:199-204 documents). Verified by repro: a destination whose Write panics causes the panic to surface directly in Writer.Write's caller, proving the Rust frames were crossed; 500 iterations survived (no abort) but the containment guarantee is violated. Realistic triggers: Rewrite() (lolhtml.go:1936-1957) hands lol-html a bytes.Buffer, whose Write panics with bytes.ErrTooLarge when growth fails; an http.ResponseWriter that panics is another. The gap is also untested: panic_test.go:30-31 says panickers holds 'one entry per //export'ed callback that can run user code' but has no entry for a panicking destination writer, and sinkfailure_test.go/faults_test.go only exercise error-returning destinations. Sink errors are parked (st.sinkErr); sink panics are not. Fix: run dst.Write through the same recover/park mechanism (return early on parked panic like the error path already does).

<details><summary>Evidence</summary>

callbacks.go:160-191: `func golol_sink_cb(chunk *C.char, n C.size_t, ud C.uintptr_t) { ... b := borrowBytes(chunk, n); written, err := cb.c.st.dst.Write(b) ... }` — no defer/recover, unlike runHandler (callbacks.go:96-103): `if r := recover(); r != nil { st.panicVal = r; d = C.LOL_HTML_STOP }`. Invariant at callbacks.go:18-20; SPEC.md:87: 'The c-api crate builds with panic = "abort"'. panic_test.go:30-77 covers every callback except this one; no panicking-destination test in sinkfailure_test.go. Repro: NewWriter(dst) where dst.Write panics -> Write never returns, panic recovered in caller's frame.

</details>

#### F-02 — No reentrancy guard: Close called from inside a handler frees the native rewriter mid-write (demonstrated use-after-free); reentrant Write aliases the rewriter and corrupts parser state

*`rewriter.go:253` — reentrancy — verified: confirmed*

Writer.Write and Writer.Close have no guard against being re-entered from a handler callback (or from the destination io.Writer invoked by golol_sink_cb), and no documentation forbids it. Write checks only closed/poisoned/len (rewriter.go:189-196); Close checks only w.closed (rewriter.go:253-258), then runs golol_rewriter_end on a rewriter still executing golol_rewriter_write on the same stack (a second Rust &mut alias — undefined behavior by Rust's rules), returns nil, and its 'defer w.c.nt.release()' frees the rewriter with lol_html_rewriter_free and deletes every cgo handle while the outer, still-running lol_html_rewriter_write continues on the freed rewriter. Demonstrated with a probe: a handler that calls w.Close() gets nil back, and the process then dies with 'runtime/cgo: misuse of an invalid Handle' raised from golol_sink_cb (callbacks.go:162) invoked by the freed rewriter — the crash is incidental, silent heap corruption is equally possible. Close's doc claim 'It is safe to call more than once' makes this an easy trap for an 'early stop' handler. Reentrant Write was also probed: the nested Write got the internal-consistency error 'Tag token should exist at this point' (real state corruption, caught by luck), poisoning the Writer — but the OUTER Write of the same document then returned (n, nil), so the failed rewrite is reported as success and only the later Close reveals ErrPoisoned; the header (internal/include/lol_html.h:276-277) says the poisoned rewriter 'must not be used again'. Fix shape: an inCall flag on Writer set around the two cgo calls, returning an explicit error (e.g. ErrReentrant) on reentry.

<details><summary>Evidence</summary>

rewriter.go:253-258: `func (w *Writer) Close() error { if w.closed { return nil } w.closed = true; defer w.c.nt.release(); ...`; rewriter.go:188-196: Write checks only `w.closed` / `w.poisoned`. Probe: handler calls w.Close() -> 'handler: Close returned `<nil>`' then 'panic: runtime/cgo: misuse of an invalid Handle' with golol_sink_cb on the stack under the still-running _Cfunc_golol_rewriter_write (rewriter.go:205). Reentrant-Write probe: nested Write returned 'lolhtml: write: Tag should exist at this point', outer Write returned (18, `<nil>`), Close reported the poison.

</details>

#### F-03 — NewWriter error paths free parsed selectors while the rewriter builder that references them is still alive, violating lol-html's documented lifetime contract

*`rewriter.go:129` — native-lifetime — verified: confirmed*

The vendored header is explicit (internal/include/lol_html.h:157-160): 'Selector SHOULD NOT be deallocated if there are any active rewriter builders that accepted it ... Deallocate all dependant rewriter builders first and then use lol_html_selector_free.' NewWriter registers `defer C.lol_html_rewriter_builder_free(builder)` (rewriter.go:126) and then, on either error path — cfg.register failing (rewriter.go:128-131) or cfg.build failing (rewriter.go:133-137) — calls c.nt.release() inline, which runs C.lol_html_selector_free on every parsed selector (rewriter.go:334-337) BEFORE the deferred builder_free runs. That is the reverse of the code's own comment at rewriter.go:124-125 ('selectors must outlive the builder, so they are released after it'), honored only on the success path; release()'s comment at rewriter.go:316-318 is likewise only true then. Realistic triggers: (a) two OnElement options where the first selector parses and is added to the builder and the second fails to parse — release frees selector #1 under the live builder; (b) any valid selector plus a bad encoding, e.g. NewWriter(dst, OnElement("p", fn), WithEncoding("utf-16")) — register succeeds, build fails, release frees all selectors under the live builder. Today's upstream builder drop only drops borrowed references without dereferencing them, so no crash is currently observable (NewWriter-error tests pass), but the code relies on an upstream implementation detail against an explicit documented contract; any future lol-html release whose builder drop touches selectors turns this into a use-after-free. Fix: free the builder before calling release() on the error paths (drop the defer and free explicitly, or split release so selectors are freed last after builder_free).

<details><summary>Evidence</summary>

rewriter.go:123-137: `defer C.lol_html_rewriter_builder_free(builder); if err := cfg.register(c, builder); err != nil { c.nt.release(); return nil, err } rw, err := cfg.build(c, builder); if err != nil { c.nt.release(); return nil, err }` — release() at rewriter.go:334-337 does `for _, s := range n.selectors { C.lol_html_selector_free(s) }`. Contract: internal/include/lol_html.h:157-160. Own comment contradicted: rewriter.go:124-125.

</details>

#### F-06 — size_t token length narrowed to C.int in string getters: >2GB token panics or silently truncates

*`strings.go:20` — integer-truncation — verified: confirmed*

takeStr and takeOptStr convert the lol-html string length (size_t) to a 32-bit C.int before calling GoStringN: `out := C.GoStringN(s.data, C.int(s.len))`. The same narrowing is in text.go:104 (GoStringN) and text.go:118 (GoBytes). These getters return whole tokens read from the untrusted document — Comment.Text, Element.Attribute / AttributeList value, Element.TagName, TextChunk.Text/Bytes. A single token longer than 2^31-1 bytes makes C.int(len) either a truncated positive value (silently truncated string, losing data) or a negative value, which makes gostringn -> unsafe.Slice panic ('slice len out of range'). Reachable from crafted input because default MemorySettings impose no cap (options.go:96 MaxMemory zero = unlimited; defaultConfig at options.go:222-235 leaves MaxMemory 0). Failure scenario: default settings, a handler reading Comment.Text or Element.Attribute on a document with one >2GB comment/attribute -> panic (DoS) or silently truncated value. Write paths are unaffected (they use C.size_t: rewriter.go:205, streaming.go:194).

<details><summary>Evidence</summary>

strings.go:20 `out := C.GoStringN(s.data, C.int(s.len))` and strings.go:31 identical; text.go:104 `return C.GoStringN(c.data, C.int(c.len))`; text.go:118 `return C.GoBytes(unsafe.Pointer(c.data), C.int(c.len))`. lol_html.h:46 `size_t len;`. options.go:96 and defaultConfig (options.go:222) leave MaxMemory unset.

</details>

#### F-20 — The runtime.AddCleanup leak backstop is defeated whenever a handler closure captures the Writer, because the global cgo.Handle table then keeps the Writer reachable forever

*`rewriter.go:144` — finalizer-gap — verified: confirmed*

core deliberately holds no pointer back to the Writer (rewriter.go:40-46) so runtime.AddCleanup(w, (*native).release, c.nt) can fire when a Writer is dropped without Close. But handler payloads are stored in the process-global cgo.Handle table (handles.go:23-27) until release() deletes them — and release() is what the cleanup was supposed to run. If a user's handler closure captures the *Writer, the chain handle-table -> cb -> fn -> Writer makes the Writer permanently reachable, the cleanup never runs, and a Writer dropped without Close leaks its Rust rewriter, selectors, and all handles for the life of the process. The documented escape (rewriter.go:141-143) silently does not apply. Worth a doc note on NewWriter/Close, since nothing can detect it at runtime.

<details><summary>Evidence</summary>

rewriter.go:140-145: `runtime.AddCleanup(w, (*native).release, c.nt)`; rewriter.go:40-46 comment: the code avoids the library-side cycle but user closures can recreate exactly that cycle.

</details>

#### F-21 — Output chunks are handed to the destination io.Writer as a zero-copy view of lol-html's internal Rust buffer; a writer that retains the slice holds a dangling native pointer

*`lolhtml.go:1984` — dangling-borrow — verified: confirmed*

golol_sink_cb passes borrowBytes(chunk, n) — an unsafe.Slice over lol-html's own buffer — directly to dst.Write. Legal under io.Writer's contract ('Implementations must not retain p') and documented internally, but the failure mode for the common real-world bug of a retaining writer (async logger, buffered tee queueing slices) is worse here than for ordinary Go callers: the retained slice points into Rust memory reused or freed after the callback returns, so a later read is a use-after-free of native memory rather than merely stale data, and invisible to the race detector. The tradeoff is deliberate and measured; the consequence of a contract-violating destination is worth stating in the Writer/NewWriter documentation, not only in an internal comment.

<details><summary>Evidence</summary>

lolhtml.go:1978-1986: `// Valid only for the duration of the call ... func borrowBytes(p *C.char, n C.size_t) []byte { return unsafe.Slice(...) }`; callbacks.go:174-178: `b := borrowBytes(chunk, n); written, err := cb.c.st.dst.Write(b)`.

## Appendix: refuted finding

One finding was raised by the memory-safety lens and killed in adversarial verification; it is recorded here so it is not re-raised in a future review.

**Claim:** Writer liveness across the cgo calls in Write/Close rests solely on the deferred releaseOnPanic call; no runtime.KeepAlive(w) protects against the AddCleanup finalizer firing mid-call

**Why it was refuted:** the verifier traced that `Writer.Write`'s post-C-call error branch stores through `w` itself (`w.poison(err)` writes `w.poisoned`/`w.cause`), so the compiler must keep `w` — and therefore the `runtime.AddCleanup` target — live across the cgo call on every path; the projected finalizer-fires-mid-call scenario is unreachable in the current code. (A `runtime.KeepAlive(w)` would still make the liveness explicit rather than incidental, but its absence is not a defect today.)
